## Открытые пункты

_На момент заполнения плана открытых пунктов нет. Будут добавляться по мере реализации, если какой-либо шаг из `@ai/tasks.md` пропускается._

### [РИСК] JSON-LD и строгий CSP

- Причина: глобальный CSP (этап 2, routes/_middleware.ts) содержит `script-src 'self'` без `unsafe-inline` и nonce. В части браузеров это может блокировать инлайн `<script type="application/ld+json">`, который рендерит components/JsonLd.tsx (этап 3).
- Ссылка: `@ai/tasks.md`, этап 3, шаг 2 (JSON-LD); этап 6, шаг 6 (подключение JSON-LD на страницах).
- Критерий готовности: на странице поста JSON-LD валиден (validator.schema.org) и не блокируется CSP - например, через CSP-hash для ld+json или подтверждение, что data-блоки не подпадают под script-src в целевых браузерах.

### [ОТЛОЖЕНО] Core Web Vitals на дашборде производительности

- Причина: F15 допускает сбор CWV "if available via browser API in admin", но PerformanceObserver в админке мерил бы сам админ-UI (гидратированные островки), а не публичные страницы - метрика вводила бы в заблуждение. Остальные метрики F15 (response time, cache hit rate, page size, KV latency) реализованы.
- Ссылка: `@ai/tasks.md`, этап 11, шаг 1 (F15).
- Критерий готовности: осознанная потребность в CWV публичного сайта и способ их собрать (например, RUM-эндпоинт, принимающий beacons с публичных страниц, при сохранении нуля JS на публичке это невозможно - потребуется отдельное решение).

### [ОТЛОЖЕНО] Сборка Docker-образа не прогонялась локально (частично проверена в CI)

- Причина: на рабочей машине нет Docker-демона, поэтому `docker build` по Dockerfile этапа 13 не выполнялся локально ни разу. Каждый шаг проверен по отдельности: deno install по deno.lock, deno task build, deno task start со scoped-правами (все зеленые локально).
- Реальный инцидент (2026-09-05, GitHub Actions, `docker/build-push-action@v6`): базовый образ был указан как `denoland/deno:2.9.6-alpine` - тег в таком порядке не существует в официальном репозитории (`docker.io/denoland/deno:2.9.6-alpine: not found`). Официальные теги идут в порядке `alpine-<version>` (например `alpine-2.9.6`), а не `<version>-alpine`. Исправлено на `denoland/deno:alpine-2.9.6` (совпадает с локальной версией Deno 2.9.6); тег подтверждён через Docker Hub API перед фиксом.
- Реальный инцидент #2 (2026-09-05, тот же workflow, следующий прогон после фикса тега): образ резолвится, `deno install` проходит, но `deno task build` (vite build -> `@tailwindcss/vite` -> `tailwindcss` -> `@tailwindcss/oxide`) падает с `Error: Cannot find native binding` внутри Alpine (musl). Первая попытка фикса - явные записи `@tailwindcss/oxide-linux-x64-musl`/`-linux-x64-gnu` в `deno.json` `imports`, чтобы получить резолвящийся root-level симлинк (по аналогии с `@tailwindcss/vite`) - **не помогла**: следующий прогон CI упал с той же самой ошибкой на том же месте, несмотря на то, что симлинк локально (Windows) подтверждённо создавался. Вывод: предположение о механике резолва `require()` внутри Deno npm-compat для транзитивных optionalDependencies было неточным (или Deno применяет иную, graph-based резолюцию, не зависящую от physical node_modules symlinks так, как в реальном Node.js).
- Настоящий фикс: прочитан реальный исходник `@tailwindcss/oxide@4.3.3/index.js` (unpkg) - пакет сам содержит официальный WASM/WASI-фолбэк на случай проваленной нативной привязки (`if (!nativeBinding) { try require('@tailwindcss/oxide-wasm32-wasi') ... }`), который срабатывает автоматически, если `nativeBinding` осталась `null` после всех попыток - никакого forced-флага не требуется. Добавлена запись `@tailwindcss/oxide-wasm32-wasi` в `deno.json` `imports` (тот же root-symlink механизм, но здесь неважно, найдёт ли Deno платформенный musl/gnu вариант - WASM работает одинаково на любой платформе). Проверено локально принудительным запуском (`NAPI_RS_FORCE_WASI=true deno task build`) - полная сборка (40+ ассетов, CSS 8.4 KB) проходит через WASM-путь без единой ошибки, что подтверждает: даже если резолв нативного биндинга в Alpine продолжит падать, WASM-фолбэк рабочий и подхватится автоматически.
- Ссылка: `@ai/tasks.md`, этап 13, шаг 1; этап 14 (аудит) не покрывал Dockerfile/deno.json, все три инцидента всплыли только при реальных прогонах CI.
- Критерий готовности: следующий прогон GitHub Actions (`docker/build-push-action@v6`) проходит `docker buildx build` целиком без ошибки resolve base image и без "Cannot find native binding"; контейнер стартует с env-переменными, отвечает на :8000, данные переживают рестарт через volume. До подтверждения зелёного CI-прогона пункт остаётся открытым - WASM-фолбэк подтверждён логически (чтение исходника oxide) и локальным forced-прогоном на Windows, но не на реальном Alpine-контейнере.

### [ОТЛОЖЕНО] Проверка гидратации островков в браузере

- Причина: smoke-тесты через curl покрывают только серверный рендер и API; реальная гидратация (события кнопок тулбара, модал медиатеки, debounce-превью) в браузере не проверялась ни на одном этапе с островками (4, 5, 7).
- Ссылка: `@ai/tasks.md`, этап 7 (MarkdownEditor), этапы 4-5 (SlugField, ConfirmDelete).
- Критерий готовности: ручной или автоматизированный (Playwright) прогон ключевых сценариев админки в браузере перед релизом MVP.

### [ЗАМЕТКА] Vite падает из-за файла NUL в корне (исправлено 2026-09-03)

- Симптом: со страницы Performance (и любой другой) переходы «не работают» - сервер мёртв, вкладка показывает кэш.
- Причина: в корне проекта оказался файл `NUL` (зарезервированное имя Windows, часто создаётся `curl -o NUL` из PowerShell). Vite при `lstat('.../NUL')` падает с `EISDIR`.
- Исправление: файл удалён через `\\.\...\\NUL`; `/NUL` добавлен в `.gitignore`. Middleware больше не ждёт полного чтения HTML перед ответом (streaming probe).

### [ЗАМЕТКА] Медленный переход на Tags/Pages в админке (исправлено 2026-09-03)

- Симптом: клик по Tags/Pages «подвисает», будто идёт долгая блокирующая операция.
- Причины: (1) Vite watcher на Windows мог видеть `data/kv.sqlite3-wal` и делать full reload посреди навигации; (2) на каждой строке списка гидрировался отдельный island `ConfirmDelete`.
- Исправление: абсолютные `server.watch.ignored` для `data/` и sqlite-файлов; один `ConfirmDeleteHost` в admin layout + серверные `ConfirmDeleteTrigger` без JS на строку.

### [ЗАМЕТКА] CSP style-src и Vite CSS (исправлено 2026-09-03)

- Симптом: админка без Tailwind (сетка/флекс не работают), Preview выглядит пустым, Theme/Focus "не реагируют" визуально.
- Причина: `csp({ useNonce: true })` переписывал `style-src` на nonce-only; Vite в dev вставляет `<style>` без nonce, стили блокировались CSP. Островки при этом гидрировались (script-src с nonce ок).
- Исправление: middleware в `main.ts` восстанавливает `style-src 'self' 'unsafe-inline'` после Fresh CSP. Script-src остаётся nonce.

### [ОТЛОЖЕНО] Валидация загрузок только по заявленному MIME, без проверки magic bytes

- Причина: `validateUpload` (lib/media.ts) сверяет `Content-Type` из multipart-запроса с расширением имени файла, но не заглядывает в реальные байты. `X-Content-Type-Options: nosniff` не даёт браузеру переинтерпретировать объявленный тип, поэтому прямой XSS через это не работает, но позволяет хранить/раздавать под доменом сайта произвольный бинарный контент под чужим расширением.
- Ссылка: `@ai/tasks.md`, этап 8 (F5, lib/media.ts), этап 14 (аудит).
- Критерий готовности: перед сохранением файла проверять сигнатуру первых байт (PNG/GIF/WebP/JPEG magic numbers; SVG — по факту валидного XML с корневым `<svg>`) и отклонять несовпадение с заявленным MIME.

### [ОТЛОЖЕНО] Timing-атака / user enumeration на `/admin/login`

- Причина: `routes/admin/login.tsx` делает `!user || !verifyPassword(...)` — при отсутствующем пользователе `bcrypt.compareSync` не вызывается, и ответ приходит существенно быстрее, чем при неверном пароле существующего пользователя. Сейчас единственный логин — `admin`, поэтому риск чисто теоретический.
- Ссылка: `@ai/tasks.md`, этап 2 (F9, routes/admin/login.tsx), этап 14 (аудит).
- Критерий готовности: перед сравнением паролей выполнять `bcrypt.compareSync` против фиктивного хеша при отсутствующем пользователе (константное время ответа независимо от существования логина) — актуально, если в проекте появится второй (editor) аккаунт.

### [ОТЛОЖЕНО] Гонка в математической капче контактной формы

- Причина: `lib/captcha.ts` делает `kv.get` + `kv.delete` не атомарно — параллельные запросы с одним token могут оба успеть прочитать ответ до удаления. Плюс пространство ответов (сумма двух цифр 1-9) — всего 17 значений, перебираемо без гонки.
- Ссылка: `@ai/tasks.md`, этап 11/13 (contact form), этап 14 (аудит).
- Критерий готовности: заменить на `kv.atomic().check(entry).delete(key).commit()` (одноразовость гарантированно) и/или расширить пространство ответов, если капча должна реально останавливать ботов, а не просто фильтровать запросы без JS.

### [ОТЛОЖЕНО] Lost-update при одновременном сохранении профиля пользователя

- Причина: `lib/users.ts` (`updateUserProfile`) и `lib/auth.ts` (`ensureAdminUser`) делают read-modify-write без `kv.atomic().check()`. Два параллельных сохранения `/admin/profile` (два открытых окна) могут потерять правки друг друга молча.
- Ссылка: `@ai/tasks.md`, этап 2 (F9, lib/auth.ts), этап 14 (аудит).
- Критерий готовности: `updateUserProfile` использует `check()` на прочитанной записи, как это уже сделано для slug-записей после этапа 14.

### [ОТЛОЖЕНО] Коллизия timestamp-ключа снапшота при двух публикациях в одну и ту же миллисекунду

- Причина: `createSnapshot` (lib/post-mutations.ts) ключует снапшот по `nowIso()` (мс-точность); если `publishPost` для одного поста вызывается дважды в пределах одной мс (двойной сабмит, гонка scheduler + ручной клик), второй снапшот молча перезаписывает первый по тому же ключу. `versionId` в типах документирован как "Timestamp (ISO 8601) of the snapshot" и используется как публичный URL-параметр (routes для просмотра/restore/diff версии), поэтому смена формата ключа ломает существующие ссылки — требует более широкого рефакторинга, чем разумно для одного прохода аудита. `postVersionMeta.count` сделан атомарным (CAS-цикл) в рамках этапа 14, коллизия самого снапшота — нет.
- Ссылка: `@ai/tasks.md`, этап 4 (F8, lib/post-mutations.ts), этап 12 (F20, scheduler + publish), этап 14 (аудит).
- Критерий готовности: развести "ключ хранения" и "versionId для отображения/URL" (например хранить снапшоты под `${timestamp}-${shortRandom}`, но продолжать резолвить по versionId через дополнительный индекс `postVersionByVersionId`), либо гарантировать, что publishPost не может быть вызван дважды для одного поста в облегающем окне (уже частично снижено фиксом гонки slug на этапе 14, но не устранено полностью).

### [ОТЛОЖЕНО] Неатомарная цепочка операций insert/delete поста — осиротевшие индексы при сбое

- Причина: `insertPost`/`deletePost` (lib/post-mutations.ts) делают основной `atomic()`-коммит, а затем несколько отдельных неатомарных вызовов (`addToList`/`removeFromList` на post_ids, `unindexPost`, `deletePostShortLink`, удаление версий). Падение процесса между шагами оставляет расхождение (например id в `post_ids` без самого поста, или наоборот). `loadPostSummaries` умеет самовосстанавливать *summary*-таблицу по количеству, но не сам `post_ids`.
- Ссылка: `@ai/tasks.md`, этап 4 (F1/F8, lib/post-mutations.ts), этап 14 (аудит).
- Критерий готовности: либо смириться (расхождение не влияет на публичный сайт, только на списки в админке, и самолечится при следующем rebuild), либо добавить фоновую сверку `post_ids` со списком реальных постов по аналогии с `rebuildPostSummaries`.

### [ОТЛОЖЕНО] `listViews` в аналитике — полный скан всех views-ключей на дашборд

- Причина: `lib/analytics.ts` (`listViews`) сканирует весь префикс `["views", kind]` при каждом открытии `/admin/analytics`. На блоге с тысячами постов с хотя бы одним просмотром это O(N) чтений на редко посещаемую admin-страницу.
- Ссылка: `@ai/tasks.md`, этап 10 (F13, lib/analytics.ts), этап 14 (аудит).
- Критерий готовности: не актуально при текущем объёме постов (десятки-сотни); при реальном росте — завести top-N индекс, обновляемый при инкременте счётчика, вместо full scan на чтение.

### [ОТЛОЖЕНО] Distributed lock для scheduler и синхронизация 60с-кэшей между несколькими инстансами

- Причина: `lib/scheduler.ts` (`startScheduler`) и module-level кэши (`lib/menu.ts`, `lib/settings.ts`, `lib/redirects.ts`) рассчитаны на один процесс. Deno KV в проекте — локальный SQLite-файл (`lib/kv.ts`), архитектура (`bootstrap()`/`startScheduler()` на старте модуля) уже предполагает single-instance деплой (docs/deployment.md); распределённая блокировка через KV понадобится только при горизонтальном масштабировании.
- Ссылка: `@ai/tasks.md`, этап 12 (F20, lib/scheduler.ts), этап 13 (деплой), этап 14 (аудит).
- Критерий готовности: осознанное решение перейти на несколько инстансов/воркеров — тогда добавить KV-лок (`atomic().check({key, versionstamp:null}).set(key, holder, {expireIn}).commit()`) для scheduler и вынести кэши на общий TTL-ключ в KV вместо module-level переменной.
